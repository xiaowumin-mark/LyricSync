# LyricSync 开发周期分段文档

## 分段原则

整个开发周期按“先闭环、再增强、最后打磨”的方式推进。

优先级：

1. 先保证应用框架、状态流和 SMTC active 会话稳定。
2. 再完成歌曲记录、本地歌词缓存和 AMLL 基础发送闭环。
3. 然后接入多平台歌词搜索和 TTML DB。
4. 最后接入 AI、细化体验、补齐测试和发布能力。

每个阶段必须有明确交付物和验收标准。阶段未验收前，不进入依赖它的下一阶段。

## 阶段 0：基线整理与架构确认

建议周期：0.5 到 1 个工作日。

### 目标

- 确认当前代码状态。
- 明确 Full 版本模块边界。
- 避免在 basic 版本代码上继续堆功能。

### 工作内容

- 梳理现有模块：
  - `internal/ui`
  - `internal/state`
  - `internal/media`
  - `internal/amll`
  - `internal/config`
- 确认 `/ref` 下参考仓库只作为参考，不直接 import。
- 确认本地数据目录、配置文件、数据库文件的存储位置。
- 明确运行时状态和持久化数据的边界。

### 交付物

- 模块拆分方案。
- 本地数据存储方案。
- 基础开发任务列表。

### 验收标准

- 能清楚说明哪些数据在内存状态里，哪些数据写入磁盘。
- 后续阶段不需要再大幅调整核心目录结构。

## 阶段 1：FluxUI 应用框架与导航

建议周期：1 到 2 个工作日。

### 目标

建立 Full 版本的 UI 骨架，替换 basic 版本的临时页面结构。

### 工作内容

- 使用 FluxUI 自带侧边导航栏。
- 建立页面路由：
  - 仪表盘
  - 会话
  - 歌曲
  - 日志
  - 设置
- 建立统一页面布局。
- 接入现有 store 订阅机制。
- 移除固定时间全量刷新 UI 的路径。

### 交付物

- 可切换的五个主页面。
- 统一的页面标题、内容区、空状态。
- UI 与运行时状态订阅打通。

### 验收标准

- 应用启动后默认进入仪表盘。
- 点击侧边导航可以稳定切换页面。
- 状态变化后 UI 自动更新，不依赖固定 interval 刷新。

## 阶段 2：SMTC 会话管理与 active 会话稳定

建议周期：2 到 3 个工作日。

### 目标

解决多个 SMTC 会话频繁切换的问题，并让用户可以手动选择主监听会话。

### 工作内容

- 完成会话页。
- 实时展示所有 SMTC 会话。
- 使用单选按钮选择 active 会话。
- 持久化用户选择。
- 手动选择后进入手动锁定模式。
- 自动模式下保持当前播放会话稳定，不频繁跳变。
- 当手动选择的会话不存在时，显示等待状态，不自动切到其他会话。

### 交付物

- 会话管理 UI。
- active 会话选择逻辑。
- active 会话持久化。

### 验收标准

- 多个播放器同时存在时，AMLL 发送的标题不会频繁变化。
- 用户手动选择会话后，重启应用仍能记住。
- 选定会话暂时消失时不会误切其他会话。

## 阶段 3：仪表盘播放体验

建议周期：2 到 3 个工作日。

### 目标

完成用户日常使用的主界面。

### 工作内容

- 展示当前 active 会话歌曲信息：
  - 标题
  - 艺人
  - 专辑
  - 封面
  - 播放状态
  - 播放进度
- 添加播放控制按钮：
  - 上一首
  - 暂停/播放
  - 下一首
- 添加音量装饰控件，暂不接真实控制逻辑。
- 展示音频波形图。
- 展示当前逐行歌词区域。
- 对空状态、暂停状态、无歌词状态做用户友好展示。

### 交付物

- 完整仪表盘。
- SMTC 控制按钮可用。
- 波形图在播放时正常显示。

### 验收标准

- 仪表盘不展示 Provider、format、frame 等开发者信息。
- 播放信息跟随 active 会话变化。
- 控制按钮能控制当前 active SMTC。
- 波形显示稳定，不明显抖动或重排。

## 阶段 4：配置、日志与基础持久化

建议周期：1 到 2 个工作日。

### 目标

补齐设置页基础能力和日志页，形成可配置应用。

### 工作内容

- 设置页实现：
  - AMLL WebSocket 地址
  - 启动后自动连接
  - 搜词优先级
  - 软件关闭行为
  - AI 服务商地址
  - AI API Key
  - AI 模型
  - 是否使用深度思考
  - 歌词清洗策略
  - AI 翻译
  - AI 音译
  - TTML DB 索引更新设置
- 日志页只展示软件自身最新 50 条日志。
- 配置修改后持久化。
- 启动时加载配置。

### 交付物

- 设置页。
- 日志页。
- 配置持久化。

### 验收标准

- 修改设置后重启仍生效。
- 日志最多保留 50 条。
- 用户能从设置页完成基础 AMLL 和歌词行为配置。

## 阶段 5：歌曲数据库与播放记录

建议周期：2 到 4 个工作日。

### 目标

记录用户播放过的歌曲，并为歌词缓存提供基础数据。

### 工作内容

- 建立本地歌曲数据库。
- 定义歌曲唯一性规则。
- active SMTC 歌曲变化时自动记录播放历史。
- 同一首歌只保留一条记录。
- 完成歌曲页最近记录展示。
- 完成全部歌曲页面。
- 支持基础 CRUD：
  - 新增
  - 编辑
  - 删除
  - 搜索
  - 查看详情
- 支持歌词预览入口。

### 交付物

- 本地歌曲数据库。
- 歌曲记录 UI。
- 全部歌曲管理 UI。

### 验收标准

- 播放新歌曲后自动进入歌曲记录。
- 重复播放同一首歌不会创建重复记录。
- 用户可以搜索、编辑、删除歌曲记录。

## 阶段 6：统一歌词结构与 TTML 能力

建议周期：3 到 5 个工作日。

### 目标

建立统一歌词模型，让不同平台歌词都能进入同一处理链路。

### 工作内容

- 参考 `/ref/amll-ttml` 设计内部歌词结构。
- 支持 TTML 解析。
- 支持 TTML 生成。
- 支持 TTML 压缩。
- 支持逐行歌词提取，用于仪表盘展示。
- 定义歌词可用性判断规则。
- 定义翻译、音译、逐词时间轴的统一字段。

### 交付物

- 内部统一歌词模型。
- TTML parse/generate/compress 能力。
- 歌词预览组件可读取统一结构。

### 验收标准

- 任意后续平台歌词都必须先转换为统一结构。
- UI 不直接依赖某个平台的原始歌词结构。
- AMLL 发送歌词时使用统一结构输出。

## 阶段 7：歌词来源接入与并行搜索

建议周期：4 到 7 个工作日。

### 目标

接入 TTML DB、QQ 音乐、网易云音乐、酷狗音乐，并按用户优先级选择可用歌词。

### 工作内容

- TTML DB：
  - 下载索引文件。
  - 默认一天更新一次。
  - 支持手动更新。
  - 支持本地索引搜索。
- 参考 `/ref/AMLX-MUSIC-API` 接入：
  - QQ 音乐
  - 网易云音乐
  - 酷狗音乐
- 并行搜索四个平台。
- 保存四个平台的原始歌词数据。
- 将各平台结果转换为统一歌词结构。
- 根据设置优先级选择最优歌词。
- QQ 音乐 `//` 翻译行按空翻译处理。

### 交付物

- 多平台歌词搜索服务。
- TTML DB 索引缓存。
- 歌词来源存储。
- 自动选择最优歌词逻辑。

### 验收标准

- 歌曲变化后能并行搜索多个来源。
- 最终应用顺序严格遵守用户设置。
- 四个平台搜索结果能被保存到本地数据库。
- 本地已有歌词时优先使用本地，不等待网络搜索。

## 阶段 8：歌词任务调度与防堆积

建议周期：2 到 3 个工作日。

### 目标

保证快速切歌时不会产生任务堆积，也不会让旧任务覆盖新歌曲。

### 工作内容

- 为 active track 引入 revision。
- 每次歌曲变化取消旧搜索任务。
- 搜索任务使用 `context.Context`。
- AI 任务使用单独限流。
- 搜索结果返回时检查 revision。
- 同一首歌重复触发做 debounce。
- 实现 latest-only 队列策略。

### 交付物

- 歌词任务调度器。
- 搜索取消机制。
- stale result 防护。

### 验收标准

- 快速连续切 10 首歌，不会把旧歌词应用到新歌曲。
- 旧任务取消后不会继续占用 UI 状态。
- AI 请求不会并发堆积。

## 阶段 9：AI 处理能力

建议周期：3 到 5 个工作日。

### 目标

接入 OpenAI 协议 AI 服务，支持歌词清洗、翻译、音译。

### 工作内容

- 实现 OpenAI 协议客户端。
- 设置页“获取模型”按钮可用。
- 支持选择模型。
- 支持深度思考开关。
- 实现 AI 歌词清洗。
- 实现 AI 翻译。
- 实现 AI 音译：
  - 仅针对非简体中文以及非英语歌词。
- AI 任务超时和取消。
- AI 失败时回退到非 AI 歌词版本。

### 交付物

- AI 服务配置。
- 模型获取与选择。
- AI 歌词增强流程。

### 验收标准

- 没有配置 AI 时，普通歌词流程不受影响。
- AI 失败不会阻塞歌曲播放和 AMLL 基础歌词发送。
- 快速切歌时旧 AI 结果不会覆盖当前歌曲。

## 阶段 10：AMLL 完整同步

建议周期：2 到 3 个工作日。

### 目标

把歌曲、封面、歌词、进度、播放状态、音量和音频数据完整同步到 AMLL。

### 工作内容

- 发送 `setMusic`。
- 发送封面 BinaryV2 `SetCoverData`。
- 发送 `setLyric`。
- 发送 `progress`。
- 发送 `paused` / `resumed`。
- 发送 `volume`。
- 发送音频 BinaryV2 `OnAudioData`。
- 手动 Send Snapshot 发送完整状态。
- 歌词准备晚于歌曲信息时，允许后续单独补发歌词。

### 交付物

- AMLL 完整发送链路。
- 手动快照完整发送。
- AMLL 连接状态展示。

### 验收标准

- AMLL 端能看到正确歌曲名、封面、歌词和进度。
- 切歌后不会残留上一首歌词或封面。
- 手动快照能恢复 AMLL 当前完整状态。

## 阶段 11：体验打磨、测试与发布准备

建议周期：4 到 7 个工作日。

### 目标

让 Full 版本达到可日常使用和可发布状态。

### 工作内容

- 补齐单元测试：
  - SMTC 选择
  - 歌曲去重
  - 歌词匹配
  - TTML 转换
  - 任务取消
  - AMLL 协议
- 补齐集成测试：
  - 歌曲变化到歌词发送完整链路
  - 本地缓存优先
  - 多平台搜索 fallback
- UI 体验检查：
  - 空状态
  - 加载状态
  - 错误状态
  - 删除确认
  - 长文本溢出
- 性能检查：
  - 高频音频波形更新
  - 歌词搜索并发
  - TTML DB 索引加载
- 发布准备：
  - 默认配置
  - 应用图标
  - Windows 打包
  - 崩溃和错误日志策略

### 交付物

- 可发布 Full 版本。
- 测试覆盖核心链路。
- 基础发布脚本或打包说明。

### 验收标准

- `go test ./...` 通过。
- 常见播放器场景可正常使用。
- 无明显 UI 重排、文字溢出或卡顿。
- 断网、AI 不可用、AMLL 未连接时应用仍能稳定运行。

## 可并行开发部分

以下工作可以并行：

- FluxUI 页面骨架与歌曲数据库设计。
- TTML DB 索引模块与设置页 UI。
- AMLL 协议发送测试与仪表盘 UI。
- AI 客户端与歌词统一结构。

以下工作不建议并行：

- SMTC active 会话逻辑和仪表盘主状态展示。
- 统一歌词结构和多平台歌词转换。
- 任务调度器和 AI 处理流程。

## 关键里程碑

### M1：Full UI 骨架可运行

包含：

- 侧边导航。
- 五个页面。
- 状态订阅。

对应阶段：1。

### M2：SMTC 稳定监听闭环

包含：

- 手动 active 会话。
- 仪表盘展示。
- 播放控制。

对应阶段：2 到 3。

### M3：本地歌曲记录闭环

包含：

- 自动记录歌曲。
- 歌曲页 CRUD。
- 歌词预览入口。

对应阶段：4 到 5。

### M4：自动搜词和歌词发送闭环

包含：

- 统一歌词结构。
- 多平台搜索。
- 本地缓存优先。
- AMLL 发送歌词。

对应阶段：6 到 8、10。

### M5：AI 增强和发布候选

包含：

- AI 清洗、翻译、音译。
- 任务防堆积。
- 完整测试。
- 发布准备。

对应阶段：9 到 11。

## 每阶段通用完成标准

每个阶段完成时至少满足：

- 功能可运行。
- 核心路径有测试或可重复验证步骤。
- 不引入明显 UI 退化。
- 不破坏已有阶段功能。
- 新增配置有默认值和持久化策略。
- 新增长任务有取消或超时策略。

## 推荐开发顺序

推荐按以下顺序执行：

1. 阶段 0：基线整理与架构确认。
2. 阶段 1：FluxUI 应用框架与导航。
3. 阶段 2：SMTC 会话管理与 active 会话稳定。
4. 阶段 3：仪表盘播放体验。
5. 阶段 4：配置、日志与基础持久化。
6. 阶段 5：歌曲数据库与播放记录。
7. 阶段 6：统一歌词结构与 TTML 能力。
8. 阶段 7：歌词来源接入与并行搜索。
9. 阶段 8：歌词任务调度与防堆积。
10. 阶段 10：AMLL 完整同步。
11. 阶段 9：AI 处理能力。
12. 阶段 11：体验打磨、测试与发布准备。

说明：AMLL 完整同步可以在 AI 之前完成。这样即使 AI 还没接入，应用也已经具备稳定的 SMTC、歌曲记录、自动搜词和 AMLL 发送主链路。
