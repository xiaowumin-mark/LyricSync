# LyricSync Full 版本开发文档

## 目标

LyricSync 不再作为 basic 版本开发，而是作为完整桌面端歌词同步工具开发。应用使用 FluxUI 框架构建主界面，使用 FluxUI 自带侧边导航栏组织页面，围绕 SMTC 会话监听、歌曲记录、歌词搜索/处理、AMLL WebSocket 发送和本地管理形成完整闭环。

核心目标：

- 实时监听用户指定的 SMTC 会话，展示当前播放信息。
- 自动记录播放过的歌曲，并为每首歌曲维护多平台歌词数据。
- 当 active SMTC 歌曲变化时，自动搜索、清洗、选择并发送最优歌词到 AMLL。
- 支持用户手动选择 SMTC 会话，避免多个 SMTC 频繁切换导致标题、歌词和 AMLL 数据抖动。
- 提供面向普通用户的仪表盘，不展示 Provider、format、frame 等开发者信息。
- 设置页集中管理 AMLL、歌词搜索、AI、TTML DB 更新等行为。

## 技术边界

- UI 框架：FluxUI。
- 导航：使用 FluxUI 自带侧边导航栏。
- SMTC 与音频采集：使用现有 `smtc-suite-go` 集成。
- 歌词搜索：参考 `/ref/AMLX-MUSIC-API`，支持 QQ 音乐、网易云音乐、酷狗音乐。
- TTML 结构：使用 `/ref/amll-ttml` 作为默认歌词结构设计参考，统一解析、生成、压缩 TTML。
- TTML DB：使用镜像站索引 `https://amlldb.bikonoo.com/metadata/raw-lyrics-index.jsonl`。
- `/ref` 下仓库只能作为参考，严禁在项目代码中直接引用 `/ref` 内部包。

## 仪表盘

仪表盘展示当前 active SMTC 会话的播放状态，是普通用户最常使用的页面。

### 展示内容

- 歌曲名称
- 专辑
- 艺人
- 封面
- 播放进度
- 播放状态
- 控制按钮：上一首、暂停/播放、下一首
- 音量控件：仅装饰展示，暂不实现真实音量控制逻辑
- 音频波形图
- 当前正在播放的歌词

### 行为要求

- 当前会话由“会话”页面的单选 active 会话决定。
- 如果当前无 active 会话，展示空状态：等待选择或等待播放。
- 播放进度应动态刷新，但 UI 更新应基于状态订阅，而不是固定时间全量刷新。
- 波形图只展示视觉效果，不显示采样率、格式、Provider、帧号等专业信息。
- 歌词为性能考虑只显示逐行歌词：
  - 当前行高亮。
  - 上下文可显示前后少量行。
  - 不渲染逐词动画。
- 控制按钮调用 SMTC 控制逻辑：
  - 上一首：previous
  - 暂停/播放：pause/play
  - 下一首：next
- 进度条先以展示为主；如果后续支持拖动，应调用 SMTC seek。

### UI 建议

- 左侧或上方为封面与当前歌曲信息。
- 中部为进度、播放控制和音量装饰控件。
- 底部或右侧为波形和逐行歌词。
- 不使用开发者术语，不暴露内部 event、format、frame、provider mode。

## 会话

会话页是简易 SMTC 管理器，用于实时查看和选择当前监听目标。

### 展示内容

每个 SMTC 会话作为一行或卡片展示：

- SMTC ID，作为唯一 ID
- 会话名称
- 歌曲名称
- 艺人
- 专辑
- 播放状态
- 播放进度，动态展示
- 是否为当前 active 会话

### 选择行为

- 使用单选按钮作为主要 active 会话选择控件。
- 用户选择后立即切换 active 会话。
- 用户选择必须持久化保存，重启后恢复。
- 当手动选择的 SMTC 会话不存在时：
  - 不自动跳到其他会话。
  - UI 显示“等待选定会话恢复”。
  - 用户可手动改选其他会话。

### 自动选择策略

- 默认可以启用自动选择。
- 一旦用户手动选择会话，应进入手动锁定模式。
- 手动模式下不因其他 SMTC 播放状态变化而切换 active 会话。
- 自动模式下优先选择正在播放的会话；若当前会话仍在播放，保持当前会话，避免频繁切换。

## 歌曲

歌曲页展示歌曲播放记录、歌词状态和歌词管理入口。

### 主页面

展示最近播放过的歌曲：

- 标题
- 艺术家
- 专辑
- 时长
- 最近播放时间
- 歌词来源状态：TTML DB、QQ、网易、酷狗
- 当前应用的歌词来源

右下角提供浮动按钮，点击后跳转到 `/songs/all` 查看全部歌曲。

### 全部歌曲页面

提供基础 CRUD 和搜索：

- 搜索歌曲：按标题、艺人、专辑模糊搜索。
- 新增歌曲记录。
- 编辑歌曲元数据。
- 删除歌曲记录。
- 查看歌曲详情。
- 预览歌词。
- 手动选择某个歌词版本并应用。

### 歌曲唯一性

每首歌曲在本地数据库唯一存在。建议使用规范化 key 去重：

- 标题：去空格、统一大小写、去常见版本后缀时保留原始值。
- 艺术家：多艺人标准化分隔。
- 专辑：可参与匹配，但不能作为唯一判断的唯一依据。
- 时长：允许误差，建议 2 到 5 秒容差。

建议唯一键：

```text
normalized_title + normalized_artist + duration_bucket
```

如无法获得时长，则退化为：

```text
normalized_title + normalized_artist + normalized_album
```

### 需要存储的数据

歌曲记录：

- ID
- 标题
- 艺术家
- 专辑
- 时长
- 封面 hash
- 首次播放时间
- 最近播放时间
- 播放次数
- 当前应用歌词来源
- 当前应用歌词 ID

歌词记录：

- 歌曲 ID
- 来源：`ttmldb`、`qq`、`netease`、`kugou`
- 原始搜索结果 ID
- 原始歌词数据
- 统一后的 TTML 数据
- 是否可用
- 是否经过软件清洗
- 是否经过 AI 清洗
- 是否包含翻译
- 是否包含音译
- 更新时间

### 歌词预览

- 预览使用逐行展示。
- 显示原文、翻译、音译。
- 对 QQ 音乐返回的翻译 `//` 视为该行无翻译，不应展示 `//`。
- 如果某平台返回音译，统一映射到内部歌词结构。

## 日志

日志页仅展示软件自身产生的日志。

要求：

- 最多保留 50 条。
- 新日志追加到顶部或底部均可，但应保持一致。
- 日志内容面向用户，避免大量技术堆栈。
- 错误日志应包含可理解的原因和用户可采取动作。

示例：

- AMLL 已连接。
- 已切换监听会话：Spotify。
- 正在搜索歌词：歌曲名 - 艺人。
- 已应用 QQ 音乐歌词。
- AI 处理超时，已使用软件清洗结果。

## 设置

设置页管理软件基础行为。

### AMLL

- AMLL WebSocket 地址。
- 启动后自动连接。

### 歌词搜索

- 搜词优先级：
  - TTML DB
  - QQ 音乐
  - 酷狗音乐
  - 网易云音乐
- 用户可调整顺序。
- 搜索时四个平台并行搜索，但选择歌词时按设置优先级逐个判断可用性。

### 关闭行为

- 软件关闭时直接退出。
- 软件关闭时最小化到系统托盘。

### AI

- AI 服务商地址，仅支持 OpenAI 协议。
- AI API Key。
- AI 模型。
- “获取模型”按钮：
  - 从用户填写的服务商地址获取模型列表。
  - 成功后供用户选择。
  - 失败时给出用户可理解的错误。
- 是否使用深度思考。
- AI 翻译。
- AI 音译：
  - 仅针对非简体中文以及非英语歌词生成。

### 歌词处理

歌词清洗策略：

- 不处理。
- 软件处理。
- AI 处理，提示延迟较大。

### TTML DB

- 更新 TTML DB 索引文件。
- 默认一天自动更新一次。
- 支持手动立即更新。
- 显示上次更新时间和索引条目数量。

## 歌词搜索与应用流程

当 active SMTC 监听到歌曲变化时，执行歌词流程。

### 主流程

1. 读取 active SMTC 当前歌曲信息。
2. 生成歌曲唯一 key。
3. 查询本地数据库。
4. 如果本地已有可用歌词：
   - 优先使用本地歌词。
   - 立即发送到 AMLL。
   - 后台可按需刷新缺失来源，但不能打断当前已应用歌词。
5. 如果本地没有可用歌词：
   - 并行搜索 TTML DB、QQ 音乐、网易云音乐、酷狗音乐。
   - 存储四个平台搜索到的歌词原始数据。
   - 将各平台歌词统一转换为内部 TTML 结构。
   - 根据设置里的搜词顺序逐个判断歌词是否可用。
   - 找到第一个可用歌词后应用。
6. 如果启用歌词清洗：
   - 软件处理：本地清洗。
   - AI 处理：提交 AI 任务，完成后替换或生成新版本。
7. 如果启用 AI 翻译或 AI 音译：
   - 在最优歌词基础上生成增强版本。
   - 保存增强版本。
   - 根据设置决定是否自动应用。
8. 将最终歌词通过 AMLL WebSocket 发送。
9. 更新歌曲数据库和 UI 状态。

### 并行搜索

搜索源包括：

- TTML DB
- QQ 音乐
- 网易云音乐
- 酷狗音乐

并行搜索只影响获取速度，不影响最终选择顺序。最终选择必须按用户设置的优先级执行。

### 可用性判断

歌词可用需要满足：

- 歌曲标题或别名匹配。
- 艺人匹配或置信度足够高。
- 时长接近。
- 至少有原文歌词。
- 时间轴可解析。
- 转换为统一 TTML 结构后没有严重错误。

如果多个结果都可用，优先级：

1. 平台优先级。
2. 标题/艺人/专辑匹配度。
3. 时长匹配度。
4. 是否包含逐词时间轴。
5. 是否包含翻译和音译。

## 统一歌词结构

内部默认结构对齐 amll-ttml 能表达的模型。

建议统一结构：

```text
LyricDocument
- metadata
- lines[]

LyricLine
- startTimeMs
- endTimeMs
- words[]
- translatedLyric
- romanLyric
- isBackground
- isDuet

LyricWord
- startTimeMs
- endTimeMs
- text
- romanText
```

所有平台歌词都必须转换成该统一结构后再进入后续处理。

### 平台差异处理

QQ 音乐：

- 可能返回原文、翻译、音译。
- 翻译为 `//` 表示该行没有翻译，应按空翻译处理。

网易云音乐：

- 可能只有 LRC。
- 翻译和原文可能需要按时间戳合并。

酷狗音乐：

- 可能返回 KRC 等格式。
- 需要解密/解析后统一到内部结构。

TTML DB：

- 优先直接解析为内部结构。
- 如果已有高质量 TTML，应优先保留逐词信息。

## 任务堆积与取消策略

歌曲切换较快时必须避免歌词任务堆积，尤其是 AI 任务。

要求：

- 每次 active track 变化生成新的 `trackRevision`。
- 歌词搜索和 AI 任务都绑定 `context.Context`。
- 新歌曲到来时取消旧歌曲未完成的搜索任务。
- 旧任务即使返回结果，也必须检查 revision，不允许覆盖当前歌曲状态。
- 搜索任务使用 latest-only 策略：
  - 队列里只保留最新 active track。
  - 同一首歌重复事件合并。
- AI 任务单独限流：
  - 默认同一时间最多 1 个 AI 任务。
  - 新歌曲切换时取消旧 AI 请求。
  - AI 超时后回退到非 AI 歌词版本。
- 对同一首歌短时间内重复触发应 debounce，建议 300 到 800 ms。

## AMLL WebSocket 发送

需要发送：

- 当前歌曲元数据：`setMusic`
- 封面：BinaryV2 `SetCoverData`，magic `0x0001`
- 歌词：`setLyric`
- 播放进度：`progress`
- 播放状态：`paused` / `resumed`
- 音量：`volume`
- 音频可视化数据：BinaryV2 `OnAudioData`，magic `0x0000`

发送原则：

- active SMTC 变化后立即发送新的歌曲信息。
- 有封面时发送封面。
- 歌词准备好后发送歌词。
- 如果歌词仍在搜索，AMLL 端可以先收到歌曲元数据和封面。
- 后续歌词完成后单独发送 `setLyric`，不需要重复发送全部状态。
- 手动发送快照时，应包含当前歌曲、封面、歌词、进度、音量和播放状态。

## 本地数据与配置

建议拆分：

- 配置文件：保存用户设置。
- 本地歌曲数据库：保存歌曲和歌词。
- TTML DB 索引缓存：保存索引文件和更新时间。

建议模块：

- `internal/config`：设置读写。
- `internal/state`：运行时状态和 UI 订阅。
- `internal/media`：SMTC、音频波形、控制。
- `internal/song`：歌曲数据库和播放记录。
- `internal/lyric`：歌词搜索、统一结构、清洗、选择。
- `internal/ai`：OpenAI 协议客户端。
- `internal/amll`：AMLL WebSocket 协议与发送。
- `internal/ui`：FluxUI 页面。

## FluxUI 页面实现要求

### 全局布局

- 使用 FluxUI 自带侧边导航栏。
- 侧边栏保持稳定宽度。
- 页面标题和内容区域统一。
- 当前路由高亮。
- 页面切换不应重置核心运行时状态。

### 状态更新

- UI 通过 store 订阅响应状态变化。
- 避免固定时间全量刷新 UI。
- 高频音频波形可单独节流或只更新波形组件。
- 歌词逐行展示应只在播放进度变化到跨行时更新高亮。

### 用户体验约束

- 仪表盘不展示开发者字段。
- 设置页字段必须有清晰标签。
- 错误提示使用用户能理解的语言。
- 删除歌曲或歌词前需要确认。
- 长任务显示状态，例如“搜索中”“AI 处理中”“索引更新中”。

## 开发阶段

- 用 FluxUI 侧边导航重构主界面。

- 接入 TTML DB 索引。

### 阶段五：歌词处理与 AI

- 实现软件歌词清洗。
- 实现 OpenAI 协议 AI 客户端。

- 发送歌曲元数据。
- 发送封面。
- 发送歌词。
- 发送进度、状态、音量和音频数据。
- 手动快照发送完整状态。

## 验收标准

- 启动应用后显示完整侧边导航：仪表盘、会话、歌曲、日志、设置。
- 仪表盘能展示当前 active SMTC 的歌曲、艺人、专辑、封面、进度、播放状态、波形和当前歌词行。
- 用户可以在会话页手动选择 active SMTC，重启后仍记住选择。
- 多个 SMTC 同时存在时，不会频繁切换 active 会话。
- 歌曲变化后自动记录到本地数据库。
- 同一首歌不会重复创建多条记录。
- 歌词搜索并行执行，但应用结果按设置优先级选择。
- 本地已有歌词时优先使用本地，不重复等待网络搜索。
- 快速切歌时旧搜索和旧 AI 任务不会覆盖新歌曲。
- 日志只保留软件自身最新 50 条。
- 设置页包含需求中列出的全部配置项。
- AMLL 能收到歌曲、封面、歌词、进度、状态、音量和音频数据。
